# Architecture

## Date partition size

Partitions are monthly by default (`PARTITION_SIZE_MONTHS=1`), matching Dagster's own built-in `MonthlyPartitionsDefinition` so a "partition" means the same thing in the scraped data as it does in the orchestration UI. A month is small enough to keep a single crawl/transform run to a manageable duration (tens of seconds to a few minutes for this site's volume) and to make re-running or backfilling one bad month cheap, but large enough to avoid excessive partition-count overhead compared to, say, daily partitions. It's a plain config value (`shared/config.py`), not hardcoded, so it can be widened or narrowed per environment without a code change.

## Retries and rate limiting

Scrapy's `AutoThrottle` replaces a fixed delay, adapting request pacing to how the server actually responds rather than a flat rate. The specific numbers (`AUTOTHROTTLE_TARGET_CONCURRENCY=4`, `AUTOTHROTTLE_START_DELAY=1`, `AUTOTHROTTLE_MAX_DELAY=30`) start from Scrapy's own defaults and only deviate where live testing against this specific site gave a concrete reason to — it responds quickly, so there's no need for Scrapy's conservative single-request-at-a-time default. `RETRY_TIMES=3` retries responses that mean "try again later" (`429`, `5xx`, `408`) while leaving permanent errors like `404` alone. `DOWNLOAD_TIMEOUT=30` fails a hung request fast rather than waiting Scrapy's default three minutes, since these are small pages that should respond in a second or two. A rotating pool of realistic desktop-browser user agents and `robots.txt` compliance round out "fast without getting blocked."

## Deduplication strategy

Two layers. First, no duplicate *records*: every save is a Mongo `update_one(..., upsert=True)` matched on `(body, identifier)`, so re-running a crawl updates an existing document in place instead of inserting a new one. Second, no wasted *writes*: before uploading or saving anything, the pipeline looks up the existing record for that document and compares its stored `file_hash` to a freshly computed one; if they match, nothing is written. That hash is computed over the document content with one specific normalization — this site embeds a per-request server rendering-time comment (`<!-- Elapsed time: ... -->`) directly in every HTML page, which would otherwise make an unchanged document hash differently on every crawl (confirmed by diffing two live fetches of the same URL). Stripping that one known-volatile comment before hashing was the fix; it's targeted at a concrete, verified problem rather than a blanket normalization.

One known limitation, left as a deliberate tradeoff: the pipeline still re-*fetches* every document over HTTP on every run, even ones that turn out unchanged — only the save is skipped. Avoiding that would need a cheap way to detect "unchanged" before paying for a full download, e.g. HTTP conditional requests. This site doesn't support that (`Cache-Control: no-cache`, no `ETag`, no `Last-Modified` — checked directly), and the one alternative signal available, `Content-Length` via a `HEAD` request, was tested and found unreliable here too: `Content-Length` itself varies between requests for the same unchanged page, for the same reason the hash did before normalization. Given that, always-fetch-but-skip-the-write is the more defensible design for this specific target, since it solves the volatility problem at the layer where the content can actually be controlled.

## Scaling to 50+ sources

The current design bakes site-specific knowledge (selectors, the search URL shape, body IDs) into one spider and one config surface. For many sources, that would need to become a per-source adapter — a shared base spider/pipeline plus a small config object per site (selectors, URL builder, item mapping), so adding a source means adding a config, not touching shared code. Partitioning would likely grow a second dimension (source × month) so each source's schedule, retries, and failures are tracked independently rather than lumped into one crawl. The subprocess-per-asset approach in `orchestration/assets.py` (one `landing_zone`/`transformed_zone` pair) would need to become source-parameterized assets, and per-source concurrency limits would matter more, so as not to let one slow or misbehaving source starve the others.

One thing already addressed rather than deferred: the Mongo/MinIO calls in `parse_document` and the item pipeline run via `twisted.internet.threads.deferToThread` + `scrapy.utils.defer.deferred_to_future` instead of blocking the reactor thread directly, so `CONCURRENT_REQUESTS`/`AUTOTHROTTLE` settings translate into real throughput rather than being serialized behind synchronous I/O. That was worth fixing now, not just at 50-source scale, since it costs nothing at today's volume and only gets more expensive to retrofit later.
